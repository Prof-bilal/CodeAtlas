# ADR-005: The Context API/SDK is a façade inside `@atlas/sdk`

Status: Accepted
Date: 2026-08-09

## Context

Task 10 ("Build the Context API / SDK") calls for a **provider-independent,
stable Context SDK** — the single interface through which CLI, MCP, editors,
and agents access a project's indexed context. Consumers must never touch the
SQLite database directly; the database is an implementation detail behind
repositories.

Today the pieces already exist independently: `@atlas/storage` owns SQLite
(repositories behind `ContextDatabasePort`), `@atlas/search` owns ranked search
behind `SearchPort`, `@atlas/summary` owns summaries behind `SummaryPort`, and
`@atlas/sdk` is the composition root that wires them all together. The CLI's
`atlas search` and the MCP server already consume only `@atlas/sdk`. But there
is **no normalized, stable façade** — consumers today reach through the
container for `getSearch()`/`getContextDb()` and shape results themselves.

Two facts constrain where the SDK can live:

1. **`@atlas/context` is the ranking/assembly seam** (ADR-001): `ContextBuilderPort`
   (rank-and-assemble for LLM prompts) is implemented as a deterministic
   rank-and-assemble step — it is *not* the query façade. Building the Context
   SDK there would conflate the two and violate ADR-001.
2. **CLI and MCP may import only `@atlas/sdk`** (enforced by ESLint). Any SDK
   that CLI/MCP/editors/agents consume must therefore be exported from
   `@atlas/sdk`.

## Decision

- Build the **Context API/SDK inside `@atlas/sdk`**, under
  `packages/sdk/src/context/`, and export `createContextSDK` from `@atlas/sdk`.
- The SDK is a **read-first façade**: normalized `Context` models (files,
  symbols, dependencies, modules, summaries, project, search, status), a
  repository layer that reads/writes **only through the `ContextDatabasePort`**
  (never SQL), a `search` sub-API delegating to `SearchPort`, a deterministic
  `getRelevantContext`, and a clearly separated **write surface** for the
  indexing pipeline.
- Reuse existing normalized types where they already exist (`Symbol`, `Summary`,
  `SearchResult`, `ContextSnapshot`) instead of redefining them; add
  SDK-specific aggregate models (`FileContext`, `DependencyContext`,
  `ModuleContext`, `ProjectOverview`, `ContextStatus`, `RelevantContext`).
- Errors are typed SDK errors (`FileNotFoundError`, `SymbolNotFoundError`,
  `ContextNotFoundError`, `DatabaseError`, `InvalidQueryError`,
  `ContextUnavailableError`) so raw database errors never leak to consumers.
- **`@atlas/context` remains the deterministic rank-and-assemble service**
  behind `ContextBuilderPort` (ADR-001). The SDK's `getRelevantContext` is a
  separate, richer deterministic assembly (search + persisted dependencies +
  stored summaries).
- `atlas search` is refactored to route through `createContextSDK` instead of
  reaching into the container for `getSearch()`/`getContextDb()`.

## Alternatives

- **Put the SDK in a new package (e.g. `@atlas/context-sdk`).** Rejected: CLI
  and MCP may import only `@atlas/sdk`; a new package would either force a
  dependency-matrix change or be unreachable from consumers. The SDK is already
  the composition root and the consumer-facing package — this is its natural
  home.
- **Implement the SDK in `@atlas/context`.** Rejected: that package is the
  ranking/assembly service (ADR-001). Folding the query façade into it would
  conflate ranking with querying and drag storage/search
  dependencies into a package that must stay port-focused.
- **Expose a `getContextSdk()` method on `Container` only.** Rejected: the
  task asks for a single clean entry point (`createContextSDK({ repositoryPath })`)
  usable without constructing a `Container` by hand; a standalone factory is
  the cleaner public surface.

## Consequences

- **Positive:** CLI, MCP, and future editors/agents get one stable interface
  (`createContextSDK`); consumers no longer shape raw rows themselves; the
  database stays hidden behind `ContextDatabasePort`; `@atlas/context`'s
  deterministic ranker is preserved behind its port.
- **Negative:** `@atlas/sdk` gains application logic (repositories, models)
  beyond pure composition — acceptable because it is the consumer-facing SDK
  package and the alternative (a new package) is blocked by the dependency
  matrix.
- **Follow-ups:** MCP handlers can be migrated to call SDK sub-APIs directly
  (reducing duplication with `@atlas/mcp`'s handlers); the indexing pipeline
  (`atlas build`/`update`) will own SDK write calls; a vector
  `RelevanceScorer` plugs into `@atlas/search` without SDK changes.
