# ADR-001: `@atlas/context` is intentionally a stub behind `ContextBuilderPort`

Status: Accepted (retroactive)
Date: 2026-08-08

## Context

The Context Engine pipeline (scan → parse → graph → store) is implemented and
tested, but `@atlas/context` (`ContextBuilderService`, the rank-and-assemble
step that picks the most relevant context to send to an LLM) throws
`ComingSoonError` from both of its methods. A naive reader could mistake this
for an unfinished bug and "fix" it by deleting the port, implementing ranking
hastily, or wiring an LLM into the ranking.

## Decision

- Keep `ContextBuilderPort` as the contract and `ContextBuilderService` as the
  structural stub, **by design**.
- Ranking/assembly ships only after the deterministic core (scanner, parser,
  graph, storage, search) is solid — aligned with the **"Deterministic Before
  AI"** principle ([PRINCIPLES.md](../PRINCIPLES.md)).
- The stub is first-class: it is wired into the default SDK `Container` and its
  tests assert `ComingSoonError`, so consumers explicitly opt into
  "context ranking not yet available."

## Alternatives

- **Delete the port entirely.** Rejected: the port is the plugin seam and future
  proof; removing it would propagate throwaway changes across `core`, `sdk`, and
  the CLI.
- **Implement a minimal ranker now.** Rejected: it would be speculative (no
  wired consumer yet) and would risk AI-gating a pipeline that must remain
  AI-optional.

## Consequences

- Any consumer of `getContext()` from a default `Container` will throw — callers
  must check `Result`/feature status before use ([FEATURE_STATUS.md](../FEATURE_STATUS.md)).
- The interface is stable, so implementing ranking later is additive, with no
  breaking changes.
- Docs (CURRENT_STATE, FEATURE_STATUS, this ADR) explicitly mark the stub so AI
  agents don't misreport it.
