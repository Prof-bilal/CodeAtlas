# ADR-004: MCP server as a dedicated `@atlas/mcp` package consuming the SDK

Status: Accepted
Date: 2026-08-08

## Context

Direction A (the Context Engine) needed a way for external AI coding tools
(Claude Desktop, Cursor, VS Code, …) to consume a project's CodeAtlas context.
The MCP server had been **[PLANNED]** in the roadmap, with no code. Two design
questions had to be settled: (1) where the server lives in the dependency
graph, and (2) whether to hand-roll the MCP wire protocol or use the official
SDK.

## Decision

- **New package `@atlas/mcp`** behind the same "thin consumer" rule as the CLI:
  it imports **only `@atlas/sdk`** (enforced by ESLint `no-restricted-imports`),
  never feature packages directly. The SDK re-exports the core types the server
  needs (`ContextSnapshot`, `Summary`, `Result`, `SummaryPort`, `SourceFile`,
  `Symbol`, `FilePath`, …).
- **Protocol:** use the official **`@modelcontextprotocol/sdk`** (MIT,
  maintained by Anthropic) as a runtime dependency, plus **`zod`** (already a
  peer of the SDK) for tool input schemas. Tool argument validation is the
  SDK's zod-schema validation (surfaced as `-32602`), with a defensive manual
  layer for cross-field rules.
- **Tools are deterministic-first.** `search_symbols`, `search_files`,
  `get_dependencies`, `explain_module`, and `project_overview` are pure reads of
  `.codeatlas/context.db`. `get_summary` reads stored summaries and only
  *generates* via AI when the caller passes `generate: true`; generation goes
  through the SDK's `SummaryPort` (i.e. whatever provider is wired in) and fails
  cleanly when no provider is configured. This keeps the server
  **provider-independent** (AGENTS.md rules 9–11).
- **Transport & logging:** stdio only. stdout is the protocol channel; all logs
  go to stderr. The context container opens lazily so the server can start
  before an index is built.

## Alternatives

- **Hand-roll the MCP stdio/JSON-RPC server.** Rejected: re-implements a
  moving wire spec, risks subtle incompatibility with real clients, and is the
  kind of "reimplement the protocol" duplication the dependency policy exists
  to avoid. The official SDK is the reference implementation and handles
  handshake, version negotiation, capabilities, and error framing.
- **Implement MCP inside `@atlas/sdk` or the CLI.** Rejected: the SDK is the
  composition root and must stay provider/interface-agnostic; the CLI is a thin
  UI. A separate package keeps ownership clean (`docs/MODULES.md`) and matches
  the roadmap's planned shape.
- **Give every tool an AI fallback.** Rejected: violates the "AI is optional"
  principle and would make the server unusable without a configured provider.
  Deterministic reads are the default; AI is opt-in.

## Consequences

- **Positive:** a testable, wire-compatible server backed entirely by existing,
  tested SDK services; protocol correctness is delegated to the canonical SDK;
  the dependency footprint is two justified runtime deps (`@modelcontextprotocol/sdk`,
  `zod`) and one workspace dep (`@atlas/sdk`).
- **Negative:** `@modelcontextprotocol/sdk` pulls a modest transitive tree
  (express, hono, zod, …) into `node_modules` for all consumers (hoisted by the
  workspace `.npmrc`), and its ESM root entry is currently broken upstream, so
  the package must be imported via `.js` subpaths.
- **Follow-ups:** wire an `atlas mcp` CLI command; add MCP resources/prompts;
  a vector scorer behind `RelevanceScorer` would improve `search_*` without
  touching the MCP layer. See [MCP.md](../MCP.md).
