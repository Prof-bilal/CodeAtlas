# ADR-007: Agent Session Manager behind `SessionPort`, composed by the SDK

Status: Accepted
Date: 2026-08-10

## Context

Task 15 (“Agent Session Manager”) builds the infrastructure to manage **many
running external AI CLI sessions at once** (Claude, Gemini, Codex, OpenCode), on
top of the Task 14 AI CLI connection layer (`@atlas/agents` behind `AgentPort`).
The manager must be provider-agnostic, keep sessions isolated, integrate with
the existing Process Runner (not re-implement spawning), and be reachable from
the CLI (`atlas sessions`).

Constraints:

1. Feature packages import **only** `core` + `shared`; `@atlas/agents` follows
   this. The session domain model and its port therefore belong in `core`.
2. `@atlas/sdk` is the only package `apps/cli` may consume (plus `@atlas/mcp`).
   For `atlas sessions` to work, the SDK must compose the connection layer —
   `@atlas/agents` was previously **not** on the SDK’s allowed-dependency list
   (a deliberate “add it when the SDK composes the connection layer” note in
   `docs/DEPENDENCIES.md`).
3. `AgentPort.run()` is a **one-shot** invocation (spawn → capture → wait →
   return). A *session* is a **long-running** process that stays alive, is
   observed on exit, and is stopped/terminated later. The connection layer needs
   a launch boundary (`ProcessRunner.launch()` returning a `RunningProcess`
   handle) without disturbing the existing one-shot `run()`.

## Decision

- Add `SessionPort`, `Session`, `SessionStatus`, `AgentId`,
  `SessionCreateRequest`, `SessionLaunchRequest` to `@atlas/core`
  (`packages/core/src/ports/session.port.ts`) as the contract for session
  management.
- Implement `SessionManager implements SessionPort` in `@atlas/agents`
  (`src/session-manager.ts`; typed errors in `src/session-errors.ts`). It
  delegates **execution** to `ProcessRunner.launch()` and **provider concerns**
  to `AgentService` (`resolveBinary`, `binaryOf`, `buildArgsFor`) — it contains
  no provider-specific switching and no process spawning.
- Extend `@atlas/agents` `ProcessRunner` with a `launch()` method returning a
  `RunningProcess` (pid, buffered `onExit`, idempotent `stop()`/`terminate()`,
  SIGTERM → SIGKILL escalation, `stdio: "ignore"` by default so a chatty child
  cannot block the session). The existing one-shot `run()` is unchanged.
- Add `@atlas/agents` to the SDK’s allowed dependencies (ESLint matrix +
  `@atlas/sdk` package.json) and expose a `createSessionManager()` factory from
  `@atlas/sdk` — the single way consumers (CLI, MCP) obtain the `SessionPort`.
- Add `atlas sessions list|info|stop` to `apps/cli` (delegating to the SDK, as
  the dependency matrix requires).
- The manager is **in-memory** (Task 15 §19): terminal sessions are pruned past
  `maxRetainedSessions` (default 100). No session database is built.

## Alternatives

- **Put the session manager in a new package (e.g. `@atlas/sessions`).**
  Rejected: the connection layer already owns spawn/supervision in
  `@atlas/agents`; a separate package would either duplicate that boundary or
  introduce a parallel Process Runner, and would widen the dependency matrix
  for no benefit. `docs/MODULES.md` already describes the orchestrator as
  “`@atlas/agents` + planned router/session manager”.
- **Make `AgentPort.run()` sessions** (one-shot only). Rejected: sessions are
  long-lived by definition; reusing `run()` would block until exit and make
  stop/terminate impossible.
- **Build a process runner inside the session manager.** Rejected: violates
  “the Process Manager owns process execution; the session manager owns session
  lifecycle” (Task 15 §8) and duplicates the security-sensitive spawn boundary.
- **Expose `atlas sessions` straight from `@atlas/agents`.** Rejected: the CLI
  may import only `@atlas/sdk`; everything must flow through the SDK.

## Consequences

- **Positive:** one clean, typed, provider-agnostic contract (`SessionPort` in
  `core`) implemented once in `@atlas/agents`; the SDK becomes the single
  composition point; `atlas sessions` works within the existing
  `cli → sdk → agents → core` dependency direction; the existing one-shot
  invocation API and all prior `@atlas/agents` behavior are unchanged.
- **Negative:** `@atlas/sdk` now also wires the connection layer (a deliberate
  dependency-matrix expansion, mirroring the pre-existing “add when composed”
  note); sessions are in-memory only, so historical session data is lost across
  processes (documented as out of scope). Piping is disabled for sessions
  (`stdio: "ignore"`), so long-running sessions do not capture output — Task 16
  may add streaming if needed.
- **Follow-ups:** Task 16 supplies real prompts/context through
  `SessionLaunchRequest`; a future task may persist sessions; interactive TTY
  attachment is a possible future `RunningProcess` enhancement.
