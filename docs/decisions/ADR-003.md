# ADR-003: Search is a dedicated `@atlas/search` module behind `SearchPort`

Status: Accepted
Date: 2026-08-08

## Context

The context pipeline (scan → parse → graph → store) persists files, symbols,
modules, dependencies, and summaries into a SQLite context database. The only
search today is `ContextStore.searchContext`, a fast DB-level `LIKE` matcher
that covers files/symbols/summaries/modules with a simple score — no fuzzy
typo tolerance, no dependency search, and no seam for semantic ranking. The
task called for a **search module**: five kinds (symbol, file, module,
dependency, summary), ranked results, fuzzy matching, and an architecture that
**prepares for vector search without shipping embeddings yet**.

## Decision

- Add a **`SearchPort` contract to `core`** and implement it in a new feature
  package **`@atlas/search`** (which imports only `core` + `shared`, per the
  dependency matrix).
- `SearchService` builds an **in-memory index from a `ContextSnapshot`**
  obtained through `ContextDatabasePort.loadContext()` — no new DB schema, no
  coupling to storage internals. It indexes:
  - symbols (name, documentation, file),
  - files (path, basename, content),
  - modules (name, path),
  - dependencies (resolved node labels + edge kind),
  - summaries (target, overview, key points).
- Ranking flows through a **`RelevanceScorer` interface**; the default
  `LexicalScorer` scores exact → prefix → whole-token → substring → fuzzy
  (Levenshtein edit distance), damping secondary fields. **The scorer
  interface is the vector-search seam**: an embedding scorer can be swapped in
  later with no caller-visible change.
- Extend the shared `SearchResult` shape (add `"dependency"` to the hit-kind
  union and an optional `relation`) so the DB's `searchContext` and the search
  module return the same public type. This is an additive, non-breaking change.
- Wire the CLI's `atlas search` to the SDK via a new
  `createProjectContainer(dbPath)` helper; it reads `.codeatlas/context.db`
  (root from `ATLAS_ROOT` or cwd), refreshes the index, and renders ranked hits.
  It reports a clean error (exit code `1`) when no index exists.

## Alternatives

- **Build search inside `@atlas/storage`.** Rejected twice: (a) storage owns
  persistence, and a ranked in-memory index is a different concern; (b) storage
  already exposes the narrow `searchContext` as a fast DB fallback, which stays
  for row-level `LIKE` needs. Keeping the two concerns separate preserves each
  package's single responsibility.
- **Ship vector search now (embeddings).** Rejected: the repo principle is
  "deterministic before AI", embeddings would require a provider/embedding
  dependency and network-optional behavior that the pipeline avoids today. The
  `RelevanceScorer` seam lets vector ranking land later additively.
- **Route dependency search through the `GraphPort`.** Rejected: the graph
  service is in-memory and unpopulated on the CLI path; the persisted
  `Dependencies` table (via the snapshot) is the reliable source, and node
  labels are resolved deterministically in the index.

## Consequences

- Callers get one ranked search surface across all five kinds; `atlas search`
  works against a persisted index.
- Fuzzy matching is deterministic and tested; no AI/embedding dependency is
  introduced.
- Adding vector search later = one new `RelevanceScorer` implementation + an
  embedding index; no `SearchPort` or caller changes.
- `searchContext` remains as the storage-level fallback; two search
  implementations coexist (storage `LIKE`, search-module ranked) and share the
  `SearchResult` type.
- Docs and feature status are updated to reflect the search module as
  **[IMPLEMENTED]**, the DB `searchContext` as a fallback, and the CLI as
  **[PARTIAL]** (only `search` wired).
