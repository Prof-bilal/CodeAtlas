# ADR-006: Agent Toolkit — curated, opt-in installation of open-source tools

Status: Accepted
Date: 2026-08-10

## Context

CodeAtlas has two directions: an implemented **Context Engine** and a mostly
planned **Agent Platform** (whose narrow AI-CLI connection layer,
`@atlas/agents`, is implemented but unwired). Users currently must research
GitHub, npm, PyPI, MCP directories, and AI-agent utilities by hand to assemble
their agent toolchain.

We want a **single trusted interface** for discovering, installing, configuring,
and verifying high-quality open-source developer / AI-agent tools — the **Agent
Toolkit**. The temptation is to build a generic "install anything from GitHub"
runner.

## Decision

- Add the **Agent Toolkit** as a first-class subsystem (Direction C):
  a **curated registry** (authoritative for what is recommended), with
  components for **manifest, compatibility, installer, configurator, and
  security/trust**.
- **Installation is opt-in.** Users approve every install; automatic
  installation is only possible under an explicit automation mode. CodeAtlas
  never blindly executes `download random repo → install.sh`.
- **Never bundle or fork third-party tools.** CodeAtlas references and installs
  them through their official distribution mechanisms (npm/pip/cargo/go/
  binary/GitHub release/MCP), and records provenance in a per-installed-tool
  **Tool Manifest**.
- Add a **security status** (`verified`/`reviewed`/`community`/`unverified`/
  `blocked`) and a **trust hierarchy**. `unverified` is the default; CodeAtlas
  does **not** claim to have audited a tool it has not.
- Functional logic lives behind **ports in `core`** (`InstallerPort`,
  `ConfiguratorPort`, compatibility, registry), implemented in the
  `@atlas/toolkit` feature package (imports only `core` + `shared`), composed
  by `@atlas/sdk`, and exposed through `atlas tools`/`/tools` in the CLI —
  consistent with existing dependency rules.
- The Toolkit reads CodeAtlas context only through the **Context SDK** and
  detects AI CLIs through the **`AgentPort`** seam that `@atlas/agents`
  implements.
- **MVP (Phase 6 first increment):** Tool Registry, Tool Manifest, Tool
  Discovery, Tool Compatibility, basic installation, basic configuration.
  **Deferred:** automatic recommendations, benchmarking, automatic token
  optimization, automatic hallucination detection, automatic selection, full
  marketplace, billing.

## Alternatives

- **Install-anything runner (npx/pipx-style world install).** Rejected: turns
  CodeAtlas into a random package installer, no curation, no security gate,
  high supply-chain risk.
- **Vendored plugin bundle** (fork third-party tools into the repo). Rejected:
  violates licensing/copyright/attribution, bloats the repository, and
  duplicates "orchestrate, don't recreate".
- **Marketplace with billing.** Rejected for MVP: heavy, not needed for the
  curated-ecosystem goal.

## Consequences

- **Positive:** a single trusted place to discover useful developer/AI-agent
  tools; incremental per-ecosystem adapters behind `InstallerPort`; security
  status explains *why* a tool is (not) recommended; strong future
  differentiator in benchmarking.
- **Negative:** registry curation is ongoing human/maintenance work; per-ecosystem
  installers are many small adapters; auto-configuration requires per-provider
  adapters that must track upstream config formats.
- **Security:** installing third-party software on the user's machine is
  high-risk — governed by `docs/SECURITY.md` (checksums/signatures for
  binary/release installs, array args, provenance recording, opt-in approval).
