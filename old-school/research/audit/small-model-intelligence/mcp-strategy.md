# MCP Strategy — Tool Surface for Weak Models

## Current tools (`packages/mcp/src/tools.ts`)

| Tool | Type | Notes |
|---|---|---|
| `search_symbols` | low-level | ranked hits, kind/doc enrichment (`handlers.ts`) |
| `search_files` | low-level | ranked file hits |
| `get_summary` | low-level | stored summaries; optional AI generation |
| `get_dependencies` | low-level | edges for a node id |
| `explain_module` | mid-level | module + files + symbols + deps + summary |
| `project_overview` | mid-level | counts, languages, top files/symbols |
| `read_file_range` | low-level | version-aware read (`expectedHash`, `stale`) |

**Weaknesses:** all low-level; the model must orchestrate
(search → id → dependencies → read) itself; no task-level entry point; no
verification; descriptions already carry behavioral warnings ("Slow. Only call
after a search narrows the target") — a symptom of tool misuse by weak models.

## Tradeoff analysis

- **Low-level only (today):** maximum flexibility; but small models fail at
  orchestration — under-calling (blind answers) or thrashing (18+ calls;
  observed in the beta audit, hence `CONTEXT_GUIDANCE` in `tool-loop.ts`).
- **High-level only:** best for weak models, but power users/hosts lose
  precision, and coarse tools can return over-large payloads.
- **Recommended: layered.** A small set of high-level tools that internally
  run deterministic pipelines, plus the existing low-level tools kept for
  precision follow-ups. High-level tools should also *return next-step hints*
  (structured `next_steps` field) so a weak model never has to decide what to
  do next from scratch.

## Proposed high-level tools (additive, keep total ≤ 12)

| Tool | Wraps | Output | Removes which model decision |
|---|---|---|---|
| `analyze_task` | TaskClassifier + entity extraction + search probes | `{category, entities, candidate_files, confidence, gaps}` | How to understand the request |
| `find_relevant_context` | closure expansion + hierarchy + budget | tiered, annotated context (files+symbols+deps+tests) with `sufficiency` verdict | What to read and in what order |
| `create_plan` | PlannerPort skeleton | `{steps, files, dependencies, tests, unknowns, verification_strategy}` | How to decompose the task |
| `inspect_symbol` | symbol + definition + callers/callees + tests | one annotated payload per symbol | How to traverse the graph |
| `verify_change` | VerifierPort | `{checks:[{name,status,detail}], verdict}` | Whether the change is safe |

Keep all 7 existing tools. Do **not** add generic `read_file`/`write_file`/
`run_command` — CodeAtlas must remain a read/context surface (security; see
`docs/SECURITY.md`); file reads of indexed files already exist via
`read_file_range` with freshness protection.

## Tool description discipline

- Every description states **when NOT to call** the tool (existing pattern,
  e.g. `read_file_range`).
- Every result carries `next_steps`: 1–3 concrete suggested calls or "answer
  now" — deterministic, generated by the handler from result state.
- Results are **size-bounded and normalized** (existing `structuredContent`
  pattern); overflow flagged (`fileOverflow` pattern in `handlers.ts`).
- Output schemas (`outputSchema`) already exist and must be kept — they give
  hosts validation and give weak models a fixed shape to imitate.

## Preventing tool overload

- Hard cap: total tools ≤ 12; prefer removing/merging over adding.
- Grouping: expose high-level tools first in `tools/list` order.
- Consistent parameter naming (`query`, `path`, `limit`) across tools —
  already mostly true; keep.
- Anti-thrash remains server-side (`SearchMemory`, per-tool caps in
  `tool-loop.ts`); MCP-side equivalents for external hosts: document + optional
  per-session caps.

## How this improves weak models

Each high-level tool replaces a multi-step orchestration (which weak models
fail at) with one call whose result is pre-annotated and pre-prioritized —
converting "use 4 tools correctly" into "call 1 tool, read the tiers".
